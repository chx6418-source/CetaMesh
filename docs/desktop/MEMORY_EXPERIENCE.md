# Conditional project experience

Memory Runtime remains the only owner of candidates, records, revisions and
review decisions. Task owns Attempts and execution evidence; Workspace supplies
current file/configuration facts; Capability Broker owns tool authorization.
An experience is bounded reference advice, never a new fact certification,
permission grant, executable Skill or Task acceptance result.

## Sources and lifecycle

The existing settled-Run observer can propose one candidate per turn and at most
three per Task. Its finite sources are an exact Owner remember/correction
statement, distinct verified repeated test failures, or a failure followed by a
fresh successful check of the current source. Owner sources are resolved from
the actual linked Chat message and Run. Model prose cannot supply that identity
or replace a missing tool receipt. Candidate identities remain deduplicated
after rejection and restart; there is no background learning model request.

Owner confirmation creates a `trial` conditional reference. Owner commands can
activate, retire, revise or roll it back using the exact current Memory revision.
The record retains at most four history snapshots and eight later observations,
with explicit omitted counts. Later machine observations do not promote advice
or claim that the advice caused a successful result. Failed writes preserve the
previous record and UI draft for an explicit retry.

Canonical optional metadata is stored under the existing `origin.experience`
namespace. The top-level `experience` value is a read projection. Older v1
readers/writers retain the origin namespace; no alternate Memory database or
destructive migration is introduced.

## Recall and continuity

Current Workspace, platform, verifier configuration and source conditions must
match before automatic recall. Existing Memory policy still restricts scope;
a reference never broadens a child Task's read contract. Recall is bounded to
three experience records, including at most one trial, inside the shared model
reference budget. Source IDs are omitted whole when necessary, not shortened
into different identities.

Chat and Managed context construction admit Memory after asynchronous Skill and
Workspace reads. They re-read current enablement, Task binding and Memory policy
before serializing. Disabling Memory while a read awaits removes the optional
references without clearing the Task or rewriting the stored Memory. Only IDs
actually retained in the final model input can receive a later Run observation.

Continuity carries exact source/revision and conditional provenance. If optional
advice is retired, unavailable or no longer matches, its body is replaced by an
explicit unavailable-reference stub while source identity remains. This does
not certify missing evidence, end the old execution or block an otherwise valid
handoff. Existing Workspace reconciliation and unknown-effect protection still
decide whether execution can continue.

An optional Owner-source read or candidate-write failure cannot skip the
existing settled handoff workflow. Errors retain bounded diagnostic codes;
completed Task/Broker evidence is not replayed to regenerate an experience.

## Validation boundaries

Registered domain and lifecycle tests cover exact signals, scopes, revisions,
deduplication, retirement and rollback. Composed Core tests use an owned local
constant model service, actual approved file writes, Node checks, retained
receipts, ordinary Chat sources, fresh-session Continuity and restart. Separate
context tests exercise Owner disable/re-enable during real Skill and Workspace
reads. Memory Workspace tests cover the maintained React review UI.

These local tests do not establish real-account, installed-product, Windows
native approval, external Provider or release-safety acceptance. Those gates
remain independent of reference recall and candidate creation.
