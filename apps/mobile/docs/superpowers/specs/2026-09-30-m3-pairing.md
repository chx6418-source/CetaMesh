# M3 Device identity and pairing

Implement the roadmap's four tasks sequentially. User requested M3 despite earlier
native gates; do not mark those gates PASS. Existing offline chat/memory must work
without a Desktop. No M4 generic capability rollout or M6 sync.

Identity: native non-exportable P-256 keys (Android Keystore, iOS Secure Enclave),
public key X9.63 uncompressed base64 and DER ECDSA/SHA256 signatures. Device ID is
native persistent metadata, independent of user identity. Only public metadata,
bounded signing, public signature verification and secure nonce generation cross
the TurboModule boundary. Unsupported hardware fails closed. No export API.

Protocol: unchanged v1 envelope fields, bounded schema validators, known types
only, unknown payloads have no side effects. Pairing QR contains HTTPS endpoint,
256-bit random token, invitation ID, peer identity/public key and <=5 minute expiry.
Mobile explicitly confirms endpoint before token transmission. A signed exchange
binds both keys, invitation, nonce and expiry. Final confirmation persists trust
only after verified peer acknowledgement; QR/token never logged or persisted.
Peer must atomically consume invitation token; local durable consumed-invitation
records reject replay across restart. No automatic network retry of exchange.

Scanner: camera.scanQr through a one-use permission policy and runtime; platform
UI owns camera lifecycle, cancellation and permission denial. Only QR text returned.

Trust: SQLite migration, bounded list/remove; every future connection authorization
must resolve current trust, and in-flight work must be cancelled on removal. No
socket/sync implementation in M3. Explicit UI confirmation, identity, trusted-device
list, delete and safe error messages. Pairing wire contract documented for Desktop;
Desktop code unchanged. Real peer interop is a separate unverified acceptance item.
